# crm-user-auth-provisioning

## Objective
A user created inside the CRM (ADMINISTRADOR, SUPERVISOR, ASESOR, VENDEDOR of an empresa) must also exist in Auth, receive a temporary password by email, log in through the Auth frontend, be forced to change the password, and be sent straight into the CRM (they only have the `crm` module; no subscription to anything else). The CRM Usuario is linked to the Auth user by `authUserId` through a trusted event, never by email.

## Decisions (user, 2026-09-21)
- Access delivery: temporary password by email (reuse Auth `createCompanyUser` + Resend). Invitation links/tokens are a later improvement.
- v1 scope: empresa-level roles only. `*_HOLDING` roles and SUPER_ADMIN are OUT of v1 (a holding user does not belong to a single Auth company).
- Linking back: Auth publishes a reply event `AuthUserProvisioned`; the CRM links by `crmUserId`. Link-on-first-login by email is rejected (Auth does not verify email ownership; takeover risk).
- Role model: Auth grants the plain `crm` module (read/create/update) through an auto-created per-company "crm-only" role; the CRM keeps `Usuario.rol` as the authorization source.
- Delivery: one feature branch per repo, stacked PRs to main, work-unit commits; push/PR/merge stay with the user.

## Event contract (topic `vimcore-domain-events`, applicationProperties `{eventType, module:"crm", correlationId}`, JSON body, MessageId = outbox row id)
- `CrmUserCreated` (CRM -> Auth): `{ crmUserId, email (normalized, the REAL login email; for empresa-level portador users it is Membresia.correo, not the synthetic Usuario.correo), fullName, authCompanyId (Empresa.authCompanyId), crmRole, correlationId, occurredAt }`. Not emitted when the empresa has no `authCompanyId` or for holding-wide roles.
- `AuthUserProvisioned` (Auth -> CRM): `{ crmUserId, authUserId | null, authCompanyId, outcome: "created" | "already_exists" | "failed", reason?, correlationId, occurredAt }`. CRM links only when `outcome="created"`, the Usuario has no `authUserId` yet, and the id matches `crmUserId`. `already_exists` leaves the user unlinked (safe default; needs authenticated acceptance later).
- Topology: new subscription `auth-crm-events` for Auth (emulator config now, Azure Bicep later); CRM keeps `crm-company-events`. Every consumer filters by `eventType` in code and completes unknown types.

## Risks
- Auth identity is single-company with a globally unique email: a person already in another Auth company cannot be added (reply `already_exists`, stays unlinked).
- Auth consumer only starts when `RESEND_API_KEY` and `RESEND_FROM_EMAIL` are set; local stack needs them or the temp-password email is not sent.
- Message TTL PT1H / MaxDeliveryCount 3 in the emulator: a down consumer can lose events; the outbox retries on the CRM side, the reply path has no retry beyond broker redelivery.
- Public change-temporary-password endpoint is a live security hole until A1 lands.
